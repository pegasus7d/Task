## Concurrency & Rate Limiting

- **Bounded concurrency at 5 in-flight cases.** `RunnerService.processRun` fans the case set out through a tiny inline limiter (`createLimiter(MAX_CONCURRENCY = 5)` in `runner.service.ts`). Implementation is a vanilla async semaphore — `acquire()` resolves when `active < limit`, queued waiters are popped FIFO on `release()`. Used `Promise.allSettled` (not `Promise.all`) so a single thrown case never bubbles out and abandons the others; per-case errors are caught inside `runOneCase` and recorded as `case_failed` increments. Why 5: matches the brief, sits well under Anthropic's default 50-req/min Haiku tier with 3-attempt retries, and keeps the per-case loop easy to reason about (no shared state across in-flight cases — each one writes to its own `(run_id, case_id, attempt_idx)` PK).
- **429 handling at the adapter boundary.** `AnthropicAdapter.call` catches `Anthropic.APIError` with `status === 429` and rethrows a typed `RateLimitError` carrying `retryAfterMs` parsed from the response's `Retry-After` header (integer seconds OR HTTP-date; falls back to 1s if missing/unparseable). The runner wraps every adapter once with `withRateLimitRetry`, which on each `RateLimitError` sleeps `min(retryAfterMs, 30s)` and retries up to **4 times** before giving up. The wrapper sits *inside* the per-case retry-with-feedback loop, so a 429 storm consumes from the 429 budget — not from the 3-attempt validation budget. Other errors (network, 5xx, schema) propagate untouched. Why this shape: idempotency replay (`extractor.service.ts` line 87) means a 429 retry never duplicates an `attempts` row even if the previous request actually reached Anthropic and was charged — the unique idempotency key reuses the in-flight row.
- **Why not Bottleneck or p-queue.** A 30-line semaphore covers the contract (`≤ 5`, FIFO, no leaked permits on throw); pulling in a dependency for that would be the single largest non-test addition to `package.json` and the brief explicitly values "the things that separate a toy from a system you'd run in CI" — i.e. correct primitives, not big libs.

## Resumability

- **`POST /api/v1/runs/:id/resume`.** `RunnerService.resumeRun(runId)` reloads the run, queries `evalRepo.completedCaseIds(runId)` (all case_ids that already have a terminal `evaluations` row — successes AND unrecoverable failures, since neither should be re-billed), filters those out of the dataset, and re-enters the same `processRun` loop on the residual set. Cases that crashed mid-attempt (a partially-written `attempts` row but no `evaluations` row) get re-queued. Their second `extractor.extract()` call computes the same content-addressed `idempotency_key`, hits `findByIdempotencyKey`, replays the stored prediction, and never calls the LLM. So resume is safe even after a power loss: zero double-charging by construction.
- **Tested**: see `concurrency-resume.test.ts` — `"completedCaseIds skips completed cases — only the rest hit the extractor"` and `"resume after a partial-write crash: idempotency replay short-circuits the surviving attempt"`.
